- Issue #529 (TM-3 follow-up, closes #529): **exact bounded replay across nightrun/shift boundaries via snapshot-on-shift-transition.** AC-1 characterization (`docs/spikes/SPIKE-529-cross-nightrun.md`, measured, 0-token) pinned the cross-shift divergence to the **active agent set** (CORE-level), with two compounding causes: R1 — `run_bounded_replay` runs only the ECS schedule, while the shift transition (despawn/respawn) is daemon-loop orchestration (`RuntimeOrchestrator::shift_transition`), not an ECS system, so a replay across a shift never reproduces it; R2 — `detect_current_shift()` is wall-clock at `time_scale == 1.0`, so the live shift fires at a non-deterministic tick. (Not the evolution result, which is redb-only and outside the ECS hash.) Rather than rebuilding the shift inside the replay (surgery on the #491 core path), the daemon now **forces an anchor snapshot immediately after every shift transition** (`SnapshotManager::mark_shift_snapshot_pending` → the periodic snapshot block captures the post-shift state at the shift tick; interval behavior otherwise unchanged). Then for any target ≥ the shift tick the nearest anchor ≤ target is the post-shift snapshot, so the replay window `(anchor, target]` is always **within a single shift** — where #491's engine is already byte-exact — and never crosses a boundary. `select_anchor_snapshot` now accepts `tick <= target_tick` (a snapshot exactly at the target = empty replay = exact post-shift state, covering `target == shift_tick`; the #528 guard rejecting `tick > target` is preserved). Additive, no change to the #491 replay/restore core; couples to #250 Tiered Retention. The R1 measurement is kept as a permanent invariant test (`replay_does_not_reproduce_shift_transition_r1`) documenting why "never replay across a shift" is the correct contract. Satisfies the TOGAF Cluster 11 mechanism (nearest anchor ≤ target + bounded replay) literally by keeping the window in scope.
- Issue #491 (TM-3, closes #491): **arbitrary tick/event restore via anchor snapshot + bounded deterministic replay** — the production Time-Machine slider for the first hour. `POST /operator/restore` now takes exactly one of `{snapshot_id}` (direct snapshot point, unchanged), `{target_tick}`, or `{target_event_id}` (`OperatorRestoreCommand::validate`; old `{snapshot_id}`-only JSON still deserializes). For a tick/event target the daemon resolves the youngest anchor snapshot `≤ target`, restores it, then deterministically replays the event range `(anchor, target]` on the live world: agent actions + operator commands (chaos/stimulus/gaia/broadcast/dm) and the PSI band are reconstructed from the event log (`source == "autonomy"` actions are skipped — the autonomy system regenerates them), and the projection is seeded from the **post-replay** state. The replay runs through the existing `FencedStateTransfer` (now carrying a `target_cursor`) under the restore fence, with side effects gated by a RAII guard that swaps the perception/action/operator channels to scratch sinks and removes the Limbo/Zenoh/redb resources (no event re-append, LLM, or NATS during replay). Honesty guards: replay only runs when the anchor is schema v3 (post-PR-A); a `snapshot_restored` event inside the range (non-linear history) or a span over the `14 400`-tick cap falls back to the nearest snapshot with `exact:false`; the `snapshot_restored` audit event records `anchor_snapshot_id`/`target_event_id`/`exact`/`replayed_inputs`. New read-only `GET /operator/state-hash` (auth-gated, via the tick-loop command pattern) returns the canonical `{strict, core, tick, last_event_id}` taken at end-of-tick — the same cycle position as the post-replay hash — so `live@T` and `restore(@T)+replay` are directly comparable. The in-process integration test `replay::tests::live_equals_restore_plus_replay` proves they match; the existing mid-commit failure-injection/rollback tests stay green (no mixed state on partial failure). `sentinel-ctl restore` gains `--target-tick`/`--target-event-id`. Builds on the #491 PR-A prerequisites below.

- Issue #75 (follow-up, closes #75): **the bwrap `--info-fd` child-PID read is now robust under a spawn burst**, so the post-spawn netns isolation verifier no longer skips agents. Live on the deploy VM (full cage otherwise green: dedicated netns, loopback only, external blocked, no error flood) ~2/26 agents during a daemon-restart respawn burst logged `bwrap did not report a sandboxed child PID via --info-fd; verification will be skipped`. Root cause (confirmed with `strace` on bubblewrap 0.9.0, not a version/timeout issue): bwrap writes the info JSON across **eight `write()` syscalls** (one per field — the first chunk `{\n    "child-pid": N` is not valid JSON on its own), and the old code did a single `poll` + single `read` + `serde_json::from_str` on the whole buffer, so under load it caught the JSON mid-sequence → parse error → `None` → skip. `read_child_pid_from_info_fd` now **accumulates across reads, re-parsing until a complete JSON object is available**, re-polling against a total deadline, and logs the exact failure mode (poll timeout / poll error / EOF-before-complete / read error) so any residual skip is classifiable on the next deploy. A `File` now owns `read_fd` (RAII close on every path), which also removes one manual `libc::close` (unsafe baseline 26 → 25). New tests: `parse_child_pid_bytes_accumulates` (incomplete buffer → `None`, complete → `Some`), `read_child_pid_reassembles_chunked_writes` (replays the real eight-chunk write sequence over a `std::io::pipe` with gaps → the loop reassembles it), `read_child_pid_eof_before_complete_returns_none`. Kept `--info-fd` (one-shot, bwrap closes after writing — no late-write `EPIPE`) rather than switching to `--json-status-fd`; the read loop is the targeted fix. The acceptance gate (daemon-restart 26-agent burst → 0 skips + the forced-`share_net` fault-injection) is re-verified live at deploy.
- Issue #535 (closes #535): **`SnapshotManager::maintain()` no longer creates a double keeper for one calendar period within a single backlogged run** — the follow-up explicitly tracked in the #250 entry below. `maintain()` reads the world-snapshot list once and never reflects its own promotions, so two hourly siblings of the same calendar day/week/month both passed `has_snapshot_for_*` (which query the stale list) and both promoted. An in-run `promoted_periods: HashSet<(u8, i64)>` (tier discriminant + calendar key: day/week = `num_days_from_ce`, month = `year*100 + month`, reusing the #250 `calendar_*_key` buckets the ACs verify) now makes a sibling whose period was already promoted this pass redundant (→ `delete_redundant`) instead of promoting again. New unit test `maintain_backlog_promotes_one_keeper_per_calendar_period` (two hourly siblings on 2024-01-05 + one on 2024-01-06 → `promoted == 2`, not 3; same-day sibling deleted; the 06th promotes independently, so the #250 day/week/month dedup regression stays green). The `retention_bench` `kalender_dups` report is upgraded to a hard `assert == 0` across all 5 cycles plus a new `correctness_backlog` scenario (deploy-VM re-measure 2026-06-15: 4 siblings/day × 5 days → `promoted=5`, `kalender_dups=0`, was `20`/`15` under the old code; `maintain` p50 2.6/12.8 ms unchanged — the in-run set is O(1) per promotion).

The helper returns `Cow::Borrowed` (no allocation) for clean values — the common case — keeping the 1:n principle (no copy when unnecessary); a settings benchmark confirms the fast path is ~3.5× faster than always-allocating. Out of scope: kernel eBPF probes (userspace is the by-design productive default, behind the `ebpf` feature flag) and the `0.0.0.0:9090` wildcard bind (#525).
- Issue #250 (closes #250): **tiered world-snapshot retention made #264-immutability-conformant and its calendar dedup corrected.** The original AC-1 (`hourly == 24`) ignored the #264 7-day immutability window — under the ransomware/anti-tamper trigger `protect_recent_snapshots` (which `RAISE(ABORT)`s any `DELETE` of a snapshot younger than 7 days), the table is already bounded at `ceil(7d / hourly_interval) + first-hour anchors` (live: hourly 177 ≤ formula bound 180; series 211→179→172→177 is non-monotonic, i.e. converged — not a leak). AC-1 reformulated to that config-derived bound + promotion correctness; **Variant B chosen** (the #264 trigger stays absolute — the daemon is the untrusted component, so retention never young-deletes, only promotes within 7 days and deletes after; a retention-approved-delete exception was explicitly rejected as it would undermine ransomware recovery). `SnapshotManager::maintain` (`services/sentinel-daemon/src/snapshot.rs`) no longer swallows the trigger block via `.unwrap_or(false)`: redundant snapshots still inside the window are **skipped** (`kept_protected`) instead of attempted-and-failed, and any trigger block that does occur is counted+logged (`delete_blocked_young` = a drift alarm) rather than discarded; real DB errors propagate. New tests: boundary invariant, trigger-error classification, week/month/day dedup reproduce-and-fix, `kept_protected`/`delete_blocked_young` paths against the real trigger, promotion preserves the restore anchor (payload/`last_event_id`/`tick` unchanged on tier UPDATE), and the #264 trigger-SQL ↔ constant SSOT linkage. - Issue #530 (closes #530): bounded replay now reproduces the **anchor's** `delta_seconds` for its per-tick time step instead of a hardcoded `1.0`, so `restore(anchor) + replay` is byte-exact at any constant `time_scale`, not only `1.0`. `replay_loop` (`services/sentinel-daemon/src/replay.rs`) read the anchor delta from the restored `SimulationTime` (set by `restore_ecs_state` from `EcsSnapshot.sim_delta_seconds`); the live loop uses `delta = tick_rate × time_scale` (`orchestrator.rs:4117`), and both `sim_hour`/`sim_delta_seconds` (hashed in STRICT+CORE) and every delta-dependent system (bio integration) would otherwise diverge under acceleration — a silent wrong-state restore, the worst failure mode for the Time-Machine guarantee. ### Known limitations at this release
- The docker compose demo intentionally exercises only the deterministic + LLM layers
  (ECS world, bio-engine, gateway pipeline, dashboard). It does **not** exercise
  the kernel-bound sandbox primitives (bwrap, Landlock, cgroups v2, netns, eBPF,
  sentinel-fs FUSE) — those need user namespaces and CAP_BPF / CAP_SYS_ADMIN that
  a plain unprivileged container does not have. The full stack is documented in
  `deploy/systemd/*.service` for VM deployment. See README "What the docker demo
  shows — and what it does not" and [docs/known-limitations.md](docs/known-limitations.md).
- The signed v0.1.0-alpha tag will display "Unverified" in the GitHub UI until the
  maintainer's SSH signing key is registered as a Signing Key on GitHub. The tag
  itself carries a valid Ed25519 signature (verifiable locally with
  `git tag -v v0.1.0-alpha`).
