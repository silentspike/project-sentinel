Cluster 01 // Strategischer Kontext

Vision

Die Vision // The Matrix SOTA

Wir bauen keine Chatbots. Wir bauen eine autonome, geschlossene Realität. Agents leben in einer diegetischen Illusion. Sie glauben Menschen zu sein, arbeiten in einem echten Büro, haben Hunger, Stress, Karriereziele und soziale Beziehungen.

Das Produktivitäts-Paradoxon:

Ein Bot ohne Angst deployt kaputten Code. Ein Agent mit Angst vor Jobverlust und Stolz auf seine Arbeit testet seinen Code dreimal. Resilienz > Geschwindigkeit.

API-Timeouts sind “Migräne”. CPU-Throttling ist “Nachmittagsmüdigkeit”. Alles wird innerhalb der Erzählung erklärt.

In einfachen Worten Stell dir die Truman Show vor, aber mit einer beliebigen Anzahl von KI-Mitarbeitern statt einem Schauspieler. Jeder glaubt, ein echter Mensch in einer echten Firma zu sein. Wir kontrollieren das Wetter, die Geräusche, sogar ob ihnen der Magen knurrt — alles ohne dass sie es merken. Ob 10 oder 200 Agents, ob Webdesign-Agentur oder Logistik-Unternehmen — die Plattform ist konfigurationsgetrieben.

Konfigurierbares Schichtmodell

Agents arbeiten in konfigurierbaren Schichten. Anzahl der Schichten, Uhrzeiten und Agent-Zuordnung werden in TOML-Konfiguration definiert. Das System unterstützt beliebig viele Schichten mit beliebig vielen Agents pro Schicht, plus optionale 24/7-Rollen (z.B. Support, Sicherheit, Betriebsrat) die keiner Schicht zugeordnet sind und durchgehend aktiv bleiben.

Schicht-SetsJeder Agent gehört zu einem shift_set (0 = 24/7, 1-N = Schichtrotation). Die Simulation erkennt automatisch welche Schicht aktiv ist und spawnt/despawnt Agents entsprechend.
SchichtwechselLetzte 15 Minuten jeder Schicht = Übergabeprotokoll. Night-Run (Gedächtnis-Konsolidierung) wird bei jedem Wechsel getriggert. 24/7-Rollen werden NIE konsolidiert.
SkalierungVon 5 Agents in einer Schicht (Minimal-Setup) bis hunderte Agents in mehreren Schichten. Die Architektur skaliert über Adaptive Scheduling — bei Hardware-Engpässen greifen diegetische Throttling-Mechanismen (Agents werden “müde”).

Research Sleep-Cycle // NMDA-inspirierte Konsolidierung SOTA

Im menschlichen Gehirn entscheiden NMDA-Rezeptoren im Hippocampus welche Erlebnisse vom Kurz- ins Langzeitgedächtnis übernommen werden. Emotionale, wiederholte und relevante Erfahrungen werden verstärkt (“Langzeitpotenzierung”), irrelevante vergessen. Unser System bildet diesen Mechanismus nach: Ein Score bewertet jede Tages-Episode und entscheidet ob sie konsolidiert wird:

LTM_Score = Relevanz × Emotionale_Intensität × Wiederholungsfrequenz × (1 / Zeitabstand)

Sleep-Cycle Ablauf (pro Agent, bei jedem Schichtwechsel)

1. Session-EndeAgent “schläft ein” — Session wird beendet, Tages-Logs gesammelt
2. Episode-ScoringNMDA-Score für jede Episode berechnet. Hoher Score = emotional, wiederholt, relevant
3. SelektionTop-N Episoden über Threshold → Kandidaten für Memory-/Profil-Updates. Rest wird vergessen
4. Night-Run UpdatesDaemon-interne Konsolidierung (nicht separater Service — vermeidet redb Lock-Konflikte). Ergebnisse in personality_evolution mit source='night_run'.
5. AufwachenAgent startet nächste Schicht mit aktualisierten Dateien/Memory-Context (kein Adapter-Swap)
In einfachen Worten Genau wie unser Gehirn im Schlaf entscheidet welche Erinnerungen bleiben und welche vergessen werden, durchläuft jeder Agent eine nächtliche “Traumphase”. Wichtige Erlebnisse (der Streit mit dem Chef, das Lob vom Kunden) prägen seine Persönlichkeit — unwichtige (dritte Tasse Kaffee) werden vergessen.

1:N ECS Pipeline v20

Externe Daten werden dedupliziert, in bevy ECS abgebildet, und den Agents als Original-Dateien präsentiert:

  → CAS-Backend (SHA-256, Segment Packs, zstd)
  → bevy ECS (1 Chunk = 1 Block in der World)
    • N Agents referenzieren denselben Block (1:N Mapping)
    • Kein Kopieren, nur Pointer
  → FUSE-Mount pro Agent
    • Agent sieht “seine Datei” als normales File
    • Read → FUSE → read_planner → CAS Lookup → Chunk aus ECS
    • Agent merkt nichts von der Virtualisierung

Dasselbe Pointer-Prinzip wie beim Time-Machine Restore: Immutable Blöcke, nur Pointer ändern sich. Low I/O, Low Latency.

Warum CAS statt btrfs Reflinks?

btrfs Reflinks brechen bei jedem Write — wenn 15 Agents npm install machen und danach schreiben, sind die CoW-Shares sofort weg. CAS arbeitet auf Hash-Ebene: identischer Inhalt = ein Blob, egal wann oder von wem geschrieben.

Validiert durch
Composefs — Kernel-CAS (Fedora/Podman), aber read-only. Wir: read-write.
AgentFS (Turso) — FUSE für AI Agents, aber ohne CAS. Wir: Inline-Dedup.
Nix Store — CA Derivations, package-level. Wir: file-level, Echtzeit.
casync (systemd) — Chunked CAS, offline. Wir: Inline bei jedem Write.

Kein existierendes System kombiniert FUSE + io_uring + Inline-CAS + redb + Multi-Agent Overlay.

BPF-Map-Strategie

Per-CPU Hash Maps

Jede CPU hat eigene Map-Kopie → kein Locking. Bei 12 Threads und N Agents: 12 × N × 24 Bytes pro Map. Bei 50 Agents ≈ 15 KB.

Ring-Buffer (256 KB)

Asynchrone Events mit variabler Rate. Ein geteilter Buffer statt per-CPU (seit Kernel 5.8). Bei Überlauf: Events dropped, Drop-Counter.

Polling-Intervall

1s für Hash-Maps (reicht für Dashboard). Ring-Buffer via epoll event-driven — kein Polling.

BTF/CO-RE Portabilität

Programme werden mit BTF (BPF Type Format) kompiliert. Der Kernel liefert Struct-Layouts via /sys/kernel/btf/vmlinux. CO-RE (Compile Once Run Everywhere): auf Build-Host kompilieren, auf VM mit anderem Kernel laden. Kernel 6.17 hat vollständiges BTF. Für VMs ohne BTF: automatischer Fallback auf Userspace-Monitoring.

Cluster 11 // Time Machine v20

Point-in-Time Restore

In einfachen Worten Wie Snapshots bei einer virtuellen Maschine. Man kann die gesamte Simulation jederzeit zu einem früheren Zeitpunkt zurücksetzen — alle Agents, alle Bio-Werte, alle Räume, alles. Ohne die Simulation neu starten zu müssen.
Pointer-basierter Restore SOTA

Events sind immutable (append-only). Ein Restore ändert keine Events — nur die Pointer (Projection Offsets, aktiver Snapshot) werden auf einen früheren Zustand gesetzt. Low I/O, Low Latency, kein Replay nötig.

Snapshots:          S_hourly_1         S_hourly_2     S_daily_1

Restore:  Pointer → S_hourly_1 (nur Offset ändern)
